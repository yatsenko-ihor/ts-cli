Перевірка після змін: `go build`, `go vet`, `gofmt -l`, `staticcheck` чисті; `go test -race ./...` проходить у 5 пакетах. `sshpass` у середовищі рев'ю недоступний, тож повний наскрізний вхід за паролем не прогонявся; механіку передачі через fd 3 перевірено на окремому процесі, а CI встановлює `sshpass`, щоб тест запиту пароля виконувався.

**Примітка щодо keychain (M‑1/M‑3).** Системне сховище (macOS Keychain, Linux Secret Service, Windows Credential Manager) дало б: шифрування ключем, який контролює ОС і який не лежить поруч із даними; розблокування разом із сеансом користувача; захист від копіювання `~/.ts-cli/` разом із бекапами. Ціна: нова залежність (напр. `github.com/zalando/go-keyring`), на Linux потрібен запущений Secret Service (GNOME Keyring/KWallet), у headless/SSH-сеансах і контейнерах його часто немає, тож потрібен файловий fallback і логіка міграції. Поточна схема з окремим ключ-файлом `0600` є розумним проміжним рішенням; keychain варто додавати як опцію, а не заміну.

## 1. Резюме

ts-cli — добре структурований застосунок на Cobra + Bubbletea. Криптографічні примітиви використані коректно (AES-256-GCM, випадковий nonce, `crypto/rand`), права на файли обмежені (`0600`/`0700`), введені користувачем SSH-логіни валідуються, секретів в історії git не знайдено. Віддаленої поверхні атаки немає: інструмент виступає лише клієнтом Tailscale API та запускає локальні бінарники.

Суттєві ризики **локальні**: збережений SSH-пароль передається у `sshpass -p` через командний рядок, де його може прочитати будь-який інший користувач хоста з таблиці процесів, а «прив'язаний до машини» ключ шифрування виводиться з публічних значень, тож збережені паролі радше обфусковані, ніж захищені. Щодо коректності, три помилки зачеплять реальних користувачів: звичайна SSH-сесія, що завершується ненульовим кодом виходу, трактується як помилка автентифікації і **видаляє збережені облікові дані**; `ts-cli install` **видаляє наявний `/usr/local/bin/tsc`**, навіть щойно визначивши, що це компілятор TypeScript; а `list --format=json` не видає валідний JSON.

## 2. Знахідки з безпеки

### H‑1 — Збережений SSH-пароль видно в командному рядку через `sshpass -p`

**Серйозність:** High  **CWE‑214** (розкриття інформації через аргументи/оточення процесу)

**Де:** `tui/ssh.go:61`, `tui/ssh.go:164`, `tui/ssh.go:217`

Кожен шлях, що використовує збережений пароль, формує `sshpass -p <відкритий текст>`. На Linux і macOS вектор аргументів процесу читається будь-яким локальним користувачем (`ps -ef`, `/proc/<pid>/cmdline`). `sshpass` намагається затерти власний argv після старту, але вікно до цього моменту та shell-обгортка в `buildSSHCommand` (запускається як `sh -c "... sshpass -p '<pw>' ssh ..."`, тому пароль також лежить в argv процесу **`sh`** протягом усієї SSH-сесії) роблять витік реальним і тривалим на спільних чи багатокористувацьких машинах.

**Виправлення:** Ніколи не передавати пароль аргументом. Варіанти:
- `sshpass -e` з паролем у змінній `SSHPASS` через `cmd.Env` (не видно в argv; `/proc/<pid>/environ` читає лише той самий користувач або root), або
- `sshpass -d <fd>` з `os.Pipe()`, переданим через `cmd.ExtraFiles` (найнадійніше: нічого ні на диску, ні в argv/env).

Для `buildSSHCommand` повністю прибрати обгортку `sh -c`: виводити банер «Connection to …» з Go перед `tea.ExecProcess`, а `sshpass`/`ssh` запускати напряму через зріз argv. Це також закриває M‑5.

### H‑2 — Будь-який ненульовий код виходу SSH видаляє збережені облікові дані й показує «connection failed»

**Серйозність:** High (коректність із побічним ефектом для безпеки: змушує користувачів повторно вводити й зберігати паролі)

**Де:** `tui/model.go:146‑163`, `tui/ssh.go:38‑43`

`tea.ExecProcess` викликає `cmd.Run()` і передає у колбек **будь-яку** помилку, включно з `*exec.ExitError` для ненульового коду виходу (перевірено у bubbletea v1.3.10, `exec.go:116‑120`). `ssh` пропагує код виходу віддаленого shell, тому цілком успішна сесія, що завершилась `exit 1`, невдалою останньою командою, вбитим віддаленим процесом або обривом мережі, повертається як `sshMsg{err}`. Обробник тоді беззастережно:

1. видаляє облікові дані машини з пам'яті та з диска, і
2. відкриває меню «SSH Connection Failed — change username/password».

Користувачі побачать, що збережений пароль зник після звичайної сесії, і їх попросять ввести його знову.

**Виправлення:** Відрізняти помилку автентифікації від інших результатів. Варіанти за зростанням надійності:
- Трактувати лише код виходу `sshpass` **5** («invalid password») та `ssh` **255** (помилка з'єднання/автентифікації) як проблему з обліковими даними; для решти `*exec.ExitError` показувати код інформаційно і зберігати дані.
- Краще: ніколи не видаляти облікові дані автоматично. Показувати меню повтору з явним пунктом «Забути збережені дані для цієї машини».

### H‑3 — `ts-cli install` видаляє наявний `/usr/local/bin/tsc` незалежно від того, що це

**Серйозність:** High (деструктивно для системи користувача)

**Де:** `commands/install.go:203‑206`

```go
// Remove existing tsc if it's ours
if _, err := os.Lstat(tscPath); err == nil {
    os.Remove(tscPath)
}
```

Коментар каже «if it's ours», але перевірки немає. `runInstall` уже визначає компілятор TypeScript (рядки 57‑69) і друкує попередження, після чого все одно видаляє його й замінює симлінком на `ts-cli`. На машині розробника це тихо ламає інструментарій TypeScript (і все, що викликає `tsc`).

**Виправлення:** Перед видаленням зробити `os.Readlink(tscPath)` і видаляти лише коли ціль — `ts-cli` (саме таку перевірку вже робить `uninstall.go:58`). Якщо `tsc` існує і не наш, пропустити аліас і повідомити про це. Варто зробити аліас опціональним (`--alias tsc`), бо `tsc` — глобально відоме ім'я.

### M‑1 — Ключ «шифрування» паролів виводиться з публічних, передбачуваних значень

**Серйозність:** Medium  **CWE‑321 / CWE‑329**

**Де:** `util/crypto.go:20‑34`; README, розділ «SSH Credential Management»

Ключ = `SHA‑256("ts-cli:<username>:<uid>:<hostname>")`. Жодне з цих значень не є секретом: ім'я користувача і hostname видно всім на машині, uid зазвичай 501/1000. Хто отримає `~/.ts-cli/config.json` (бекап, папка синхронізації, образ викраденого ноутбука, витік репозиторію dotfiles), за секунди відтворить ключ офлайн. Твердження README, що паролі «cannot be decrypted on another machine or by another user», **неточне**; реальний захист — це режим файлу `0600` і те, що пароль не лежить у відкритому вигляді.

Побічний ефект: на macOS `os.Hostname()` часто змінюється залежно від мережі (імена від DHCP), а користувачі перейменовують машини. Тоді `DecryptPassword` падає, `getMachinePassword` тихо повертає `""`, і TUI відкочується до звичайного `ssh`, питаючи пароль, який «нібито» має. Жодної діагностики.

**Виправлення:**
- Бажано: зберігати SSH-пароль (і API-ключі Tailscale) у системному сховищі облікових даних (macOS Keychain, Linux Secret Service, Windows Credential Manager) через бібліотеку на кшталт `github.com/zalando/go-keyring`.
- Якщо файлову схему треба лишити: один раз згенерувати випадковий 32-байтний ключ, зберігати його з правами `0600` у `~/.ts-cli/key` і використовувати для AES‑GCM. Це хоча б відокремлює ключ від шифротексту й усуває крихкість через hostname. Чесно задокументувати, від чого схема захищає, а від чого ні.
- У будь-якому разі при невдалому розшифруванні показувати один рядок попередження («збережений пароль для X не вдалося розшифрувати на цьому хості; введіть знову, щоб зберегти»).

### M‑2 — API-ключ Tailscale передається у командному рядку в сценарії додавання акаунта

**Серйозність:** Medium  **CWE‑214**

**Де:** `tui/tailscale.go:150`

Згенерований bash-скрипт виконує `ts-cli login --tailnet="$TAILNET" --api-key="$API_KEY"`. Ключ видно в таблиці процесів протягом усього (мережевого) виклику `login`. В іншому скрипт акуратний (`read -s`, тимчасовий файл `0700`, видаляється після виконання).

**Виправлення:** `login` уже читає `TAILSCALE_API_KEY` з оточення. Змінити скрипт на `TAILSCALE_API_KEY="$API_KEY" ts-cli login --tailnet="$TAILNET"`. Варто прибрати прапорець `--api-key` з документації/прикладів на користь змінної оточення або інтерактивного вводу, бо прапорці також осідають в історії shell.

### M‑3 — API-ключі Tailscale та SSH-паролі зберігаються в одному JSON-файлі

**Серйозність:** Medium (дизайн)

**Де:** `commands/config.go:19‑30`, `tui/config.go:107‑118`

API-ключі зберігаються у відкритому вигляді (стандартно для CLI, але варто про це сказати) разом із зашифрованими SSH-паролями, SSH-логінами та списком машин. Компрометація одного файлу дає повний контроль над кожним налаштованим tailnet (API-ключ може авторизувати/деавторизувати пристрої, змінювати ACL тощо залежно від scope). Див. M‑1 щодо keychain; щонайменше задокументувати в README, що конфіг містить живі адміністративні облікові дані, і його не варто синхронізувати чи бекапити без шифрування.

### M‑4 — Гонка даних між циклом оновлення Bubbletea та фоновими горутинами команд

**Серйозність:** Medium (можлива паніка / пошкоджений файл історії)

**Де:** `tui/ssh.go:159‑192` (`executeRemoteCommand`), `tui/handlers.go:317‑337` (`cmdHistoryDelete`), `tui/model.go:152` та `tui/handlers.go:883` (мутація мапи)

Замикання, яке повертає `executeRemoteCommand`, виконується в окремій горутині і (a) читає `m.ssh.machineCreds` через `getMachinePassword`, та (b) мутує спільний `*util.HistoryStore` (`AddCommand`, `Save`). Тим часом `Update` може зробити `delete()` з тієї ж мапи (одночасний read/write мапи в Go — фатальна помилка рантайму, а не відновлювана гонка), а `cmdHistoryDelete` може мутувати й зберігати той самий `HistoryStore`. `model` — значення, але мапа і вказівник усередині спільні.

**Виправлення:** Отримувати пароль і будувати повний `*exec.Cmd` синхронно всередині `executeRemoteCommand` до повернення замикання (замикання має лише запускати команду). Повертати запис історії в `commandExecutedMsg` і давати `Update` додавати/зберігати його в головному циклі, або додати м'ютекс усередину `HistoryStore`.

### M‑5 — Shell-обгортка підставляє неекранований SSH-таргет; логін з диска не валідується повторно

**Серйозність:** Medium (глибинний захист; експлуатується лише тим, хто вже може писати в конфіг користувача або контролювати відповіді API)

**Де:** `tui/ssh.go:66‑73`

`buildSSHCommand` запускає `sh -c` із сирим `sshTarget` (`user@ip`). `ValidateSSHUsername` застосовується лише до логінів, введених у промпті; логіни з `config.json` (`ssh_username`, `machine_credentials[*].username`) приймаються як є, а `Addresses[0]` приходить з API. Значення на кшталт `x;curl …|sh` виконається. Межі довіри роблять це малоймовірним, але усунення (без shell) безкоштовне і водночас виправляє H‑1.

**Виправлення:** Як у H‑1, прибрати `sh -c` і передавати зріз argv у `exec.Command`. Додатково валідувати логіни під час завантаження конфігу й перевіряти кожну адресу через `net.ParseIP`.

### M‑6 — `login` тихо відкидає нечитабельний конфіг і перезаписує його

**Серйозність:** Medium (втрата ключів інших акаунтів)

**Де:** `commands/login.go:68‑75`

Якщо `LoadConfig()` повертає помилку (наприклад, один зіпсований байт у JSON або тимчасова проблема з правами), `login` створює порожній `Config`, і `SaveConfig` перезаписує наявний файл, знищуючи всі інші збережені акаунти. Коментар («If config doesn't exist, create a new one») хибний: відсутній файл уже повертає порожній конфіг без помилки; у цю гілку можна потрапити лише з пошкодженим або нечитабельним файлом.

**Виправлення:** Повертати помилку. Якщо потрібен шлях відновлення — зробити бекап (`config.json.broken-<timestamp>`) перед перезаписом і повідомити користувача.

### M‑7 — Tailnet підставляється у шлях URL API без екранування

**Серйозність:** Medium (низька експлуатованість; шкода лише собі)

**Де:** `client/tailscale.go:87`, `client/tailscale.go:111`

`fmt.Sprintf("/tailnet/%s/devices", tailnet)` без `url.PathEscape`. `ValidateTailnet` перевіряє лише наявність `@`/`.` і довжину, тому значення з `/`, `?`, `#` чи `%` доходять до рядка запиту і змінюють ендпоінт. Значення контролює лише користувач, отже це не вектор атаки, але воно породжує незрозумілі помилки API і стане небезпечним, якщо імена tailnet колись братимуться з інших джерел.

**Виправлення:** `url.PathEscape(tailnet)`; додати `context.Context` з дедлайном у `doRequest` і обмежити читання тіла через `io.LimitReader`.

### M‑8 — Пароль записується на диск до спроби з'єднання

**Серйозність:** Medium (компроміс дизайну; позначено для уваги)

**Де:** `tui/handlers.go:1004‑1016`

Введений пароль шифрується і пишеться у `config.json` **до** запуску `ssh`, а очищення покладається на (помилковий) шлях відмови з H‑2. Тож неправильно введений пароль зберігається, а якщо TUI вбито посеред сесії — лишається. Коментар у коді пояснює намір (пережити закриття терміналу). Разом із H‑2 це створює заплутані стани.

**Виправлення:** Коли H‑2 почне розрізняти помилки автентифікації, це прийнятно. Альтернатива — тримати пароль у пам'яті і зберігати після першого успішного `sshMsg{err: nil}`; закритий термінал коштуватиме користувачу одного повторного вводу.

### L‑1 — `StrictHostKeyChecking=accept-new` застосовується лише на шляху з sshpass

**Серйозність:** Low

**Де:** `tui/ssh.go:61`, `165`, `218` проти `66`, `169`, `222`

Поведінка відрізняється залежно від того, чи збережено пароль, і це дивно. `accept-new` — розумний дефолт для IP Tailscale (стабільна, автентифікована мережа); застосовувати послідовно або не застосовувати взагалі; `-o UserKnownHostsFile` ізолювати лише за запитом користувачів.

### L‑2 — Скрипт додавання акаунта: через `set -e` гілка помилки недосяжна; на Windows bash-скрипт запускається через `cmd /c`

**Серйозність:** Low

**Де:** `tui/tailscale.go:96`, `152‑163`, `191‑192`

Із `set -e` ненульовий вихід `ts-cli login` зупиняє скрипт до `if [ $? -eq 0 ]`, тож повідомлення «Failed to add account. Press Enter…» ніколи не з'являється. На Windows згенерований bash-скрипт передається у `cmd /c`, який не може його виконати. Прибрати `set -e` (або обгорнути login у `if ! …; then`) і або пропускати функцію на Windows, або генерувати PowerShell-еквівалент.

### L‑3 — Ручний парсинг JSON з `tailscale status --json` може взяти не того користувача

**Серйозність:** Low (коректність евристики перемикання акаунтів)

**Де:** `tui/tailscale.go:238‑256`

Код повертає перший рядок `"LoginName"` у документі. У `tailscale status --json` `LoginName` лежить у мапі `User` (ключ — ID користувача), яка містить кожного користувача, чиї вузли вам видні, включно з власниками shared-вузлів. Поточний логін — це `User[Self.UserID].LoginName`. Парсити через `encoding/json` у структуру з `Self.UserID` і `User map[string]struct{ LoginName string }`.

### L‑4 — Запуск зовнішніх `sleep` та `which`

**Серйозність:** Low

**Де:** `commands/ssh.go:109`, `commands/tailscale_check.go:106`, `tui/tailscale.go:321`

Використовувати `time.Sleep` і `exec.LookPath`; обидва портативні й не породжують процесів (`which` відсутній у деяких мінімальних образах Linux і на Windows).

### L‑5 — Вивід у stderr під час перезавантаження в TUI псує alt-screen

**Серйозність:** Low

**Де:** `client/tailscale.go:173`, викликається з `tui/model.go:130`

`ListDevicesFromAccounts` друкує попередження у stderr. При виклику з TUI (клавіша `r`) це пише сирий текст прямо в alt-screen Bubbletea. Повертати помилки по акаунтах викликачу й давати TUI рендерити їх через `notify.sshError`.

### L‑6 — Довжина маски пароля рахується в байтах, а не в рунах

**Серйозність:** Low (косметика, нічого суттєвого не витікає)

**Де:** `tui/view.go:522`

`strings.Repeat("•", len(value))` показує більше крапок, ніж символів, для не-ASCII паролів. Використати `utf8.RuneCountInString`.

## 3. Знахідки щодо коректності та поведінки (не безпека)

### C‑1 — `list --format=json` видає невалідний JSON

**Де:** `commands/list.go:148‑167`

Вивід будується через `fmt.Printf`: рядки не екрануються (`"` в імені пристрою ламає документ), а `addresses` друкується через `%v`, що дає `[100.64.0.1 fd7a::1]` — це не JSON. `internal/formatters.FormatAsJSON` уже робить це правильно через `encoding/json`, але не використовується. Замінити тіло на `json.NewEncoder(os.Stdout).SetIndent(...); Encode(devices)`.

### C‑2 — Користувачів із ключовою автентифікацією щоразу змушують вводити пароль

**Де:** `tui/handlers.go:770‑787`; README, «Connection flow», крок 2

README каже: «No per‑machine creds, global username exists → try connecting (key‑based auth)». Код натомість завжди відкриває промпт пароля, коли логін є, а пароля для машини немає. Порожній Enter ігнорується, тож єдиний спосіб спробувати key-auth — Esc (який скасовує). Або реалізувати задокументовану поведінку (спробувати звичайний `ssh`, питати пароль лише після невдачі), або оновити README і додати явний пункт «підключитися без пароля».

### C‑3 — Запис конфігу з TUI відкине невідомі поля верхнього рівня

**Де:** `tui/config.go:107‑112`

`configJSON` віддзеркалює чотири поля `commands.Config` і використовує `json.RawMessage` для акаунтів. Будь-яке майбутнє поле `commands.Config` (або записане іншим інструментом/версією) тихо втрачається щоразу, коли TUI зберігає логін чи облікові дані. Зараз структури синхронні, тож проблема латентна. Виправити винесенням I/O конфігу в спільний пакет (наприклад, `internal/config`), який імпортують і `commands`, і `tui`; це також прибере дубльований код load/save і непослідовність із `configMu`, що існує лише в одному пакеті.

### C‑4 — Різна семантика зіставлення акаунтів

**Де:** `commands/config.go:169` (за `Tailnet`), `commands/login.go:81` (за `Name` **або** `Tailnet`), `commands/account.go:103,155` (за `Name` або `Tailnet`), `internal/services/config_service.go:93` (за `Name`)

Різні шляхи коду по-різному вирішують, що таке «той самий акаунт». Обрати один ключ (природно — tailnet) і проводити всі мутації через `Config.AddAccount`/`SetActiveAccount`.

### C‑5 — `d` у переліку збережених облікових даних спрацьовує також на Backspace

**Де:** `tui/handlers.go:879`

Backspace — несподівана деструктивна клавіша у списку, і її легко натиснути рефлекторно після Esc із текстового промпту. Лишити тільки `d`/`delete` або вимагати підтвердження.

### C‑6 — Непослідовні ключі ідентифікації машин

**Де:** `tui/handlers.go:739` (облікові дані за `Name`, fallback `Hostname`) проти `tui/ssh.go:154` та `tui/handlers.go:288` (історія за `ID`, fallback `Hostname`)

Облікові дані та історія для одного пристрою використовують різні ключі. `Name` (FQDN) змінюється при перейменуванні; `ID` стабільний. Стандартизувати на `ID` з одноразовою міграцією наявних ключів.

### C‑7 — Install/uninstall ігнорують `GOBIN`/`~/.local/bin` і потребують root

**Де:** `commands/install.go:89`

Жорстко заданий `/usr/local/bin` потребує `sudo` на більшості систем; бінарник стає root-овим, а конфіг лишається в домашній теці користувача. Віддавати перевагу `~/.local/bin` (XDG), коли `/usr/local/bin` недоступний для запису, і повідомляти, що обрано.

## 7. Що зроблено добре

- AES‑256‑GCM використано коректно: свіжий випадковий nonce на кожне шифрування, nonce на початку, автентифіковане розшифрування, перевірка довжини перед зрізом (`util/crypto.go`).
- Тека конфігу `0700`, файли конфігу/історії `0600`; тимчасовий скрипт додавання акаунта `0700` і видаляється після використання.
- Валідація SSH-логіна (`^[a-zA-Z0-9._-]+$`, без початкового `-`, ≤32 символів) блокує ін'єкцію опцій у `ssh`.
- Усі виклики `exec.Command`, крім однієї обгортки `sh -c`, передають зрізи argv, а не shell-рядки.
- `StrictHostKeyChecking=accept-new`, а не `no`.
- API-ключ приймається з оточення, а `login` валідує ключ через API перед збереженням.
- Санітизація вставки з буфера обміну прибирає керівні символи та переноси рядків перед вставкою в однорядкові промпти.
- Чітке розділення стану TUI на підструктури та дизайн обробників клавіш через таблиці диспетчеризації, які легко читати й тестувати.
